## Speicher-Limit der Sandbox: 128 MB
- **Speicher-Limit der Sandbox: 128 MB** (Angabe des Nutzers aus seiner Anzeige; 1 MB = 1 048 576 Bytes). Gezählt wird der Arbeitsordner samt `.git`. Nicht mitgezählt – und nach einem Reset weg – sind `node_modules`, `dist`, alle Ordner namens `out`, `.npm`, `.cache` und `.git/config`. **Über dem Limit geht der Stand verloren:** am 2026-11-22 war nach einem Reset der letzte lokale Commit weg – `.git` stand wieder vor dem Commit, die Dateien im Arbeitsordner waren noch da. Gemessen: mit dem Commit 130,6 MB, ohne ihn 117,3 MB – genau der Wert, den die Anzeige des Nutzers danach noch zeigte. Dass das Limit die Ursache war, ist daraus geschlossen, nicht bewiesen.
  - **Ursache der Größe (bis 2026-11-22):** `tools/harness/out/game.js` war versioniert. Jedes neu gebaute Bundle landete bei `git add`, `git commit` und `git stash` als loses Objekt von 12,3 MB in `.git/objects`. Sechs davon lagen dort (vier aus Commits, zwei aus verworfenen Zwischenständen mit `git stash`) – `.git` war 105,8 MB groß. Seitdem sind die Bundles nicht mehr in Git; die alten Fassungen stecken weiter in der Historie (siehe „Reserve").
  - **Regel: nach jedem Commit `git gc --prune=now`** (≈ 5 s) – so bleibt `.git` ein einziges Paket. Prüfen: `git count-objects -vH` – `size` (lose Objekte) muss `0 bytes` sein. Danach muss `.git/refs/.keep` noch da sein (`ls -a .git/refs`) – sonst erkennt git das Repo nach dem nächsten Reset nicht mehr (siehe „After a sandbox reset").
  - Für Vergleiche mit einem älteren Stand: `git show <Commit>:<Pfad>` oder `git archive <Commit> | tar -x -C /var/tmp/<Ordner>`. (Die frühere Regel „kein `git stash` mit neu gebautem Bundle" ist seit dem 2026-11-22 hinfällig: die Bundles sind ignoriert.)
  - **`npm run save` ist abgeschaltet** (2026-11-22, Entscheidung des Nutzers: „erstmal"). `tools/save.sh` gibt gleich am Anfang eine Meldung aus und endet mit Exit-Code 1 – nichts wird committet, nichts geschrieben (geprüft: `HEAD`, `git status` und der Arbeitsordner bleiben gleich). Grund: das Skript legte drei Kopien von `.git` an (gemessen: 123 MB zusammen). **Wieder einschalten nur auf Wunsch des Nutzers:** den markierten Block am Anfang von `tools/save.sh` löschen (bis zur Zeile „end of switch"); der Rest des Skripts ist unverändert. `package.json` wurde dafür nicht angefasst. Der Nutzer hat am 2026-11-22 noch einmal entschieden: **abgeschaltet lassen**. Ob das Skript ganz entfernt wird, bleibt offen (`TODO.md`).
  - `npm run restore-git` ist **nicht** abgeschaltet. Drei Fälle (alle am 2026-11-23 in Probe-Ordnern getestet): (1) `.git` funktioniert → nichts zu tun, nach einem Reset schreibt es die verlorene `.git/config` neu; (2) nur der Ordner `.git/refs` fehlt → es legt ihn an, **nichts geht verloren** (siehe „After a sandbox reset"); (3) `.git` fehlt ganz oder ist nicht zu reparieren → es holt den Ordner von GitHub, Zweig `dev` – nie gepushte Commits sind dann weg, lokale Änderungen erscheinen als geändert. Ein unbrauchbares `.git` wird dabei nach `.git.kaputt-<Zeit>` **verschoben, nie gelöscht** (ignoriert in `.gitignore`; zählt zum Speicher-Limit – erst löschen, wenn sicher nichts Ungepushtes darin liegt).
  - **Ganz neu packen** (am 2026-11-22 einmal gemacht, 38,7 → 33,2 MB): `git -c pack.threads=1 -c pack.windowMemory=500m repack -a -d -f --window=50 --depth=50`, danach `git fsck --full`. Größere Fenster bringen nichts mehr (33,1 MB).
  - **Stand nach dem Aufräumen (2026-11-22): rund 48 MB.** `.git` 33 MB (neuestes Bundle 11,9 · Texturen 11,2 · die gelöschte Text-Sicherung in der Historie 7,8 · alles andere 2,4), `src` 12,4 MB (davon Texturen 11,2), `.archiv` 1,3 MB.
  - **Reserve, falls es wieder eng wird** (nicht gemacht): die lokale Historie kürzen (`git fetch --depth 1`). Das bringt rund 21 MB: 8,6 MB alte Text-Sicherung und 12,4 MB alte Harness-Bundles, die seit dem 2026-11-22 nicht mehr im aktuellen Stand liegen (gerechnet aus den Messungen vom 2026-11-22, nicht neu gemessen). Die alte Historie bliebe auf GitHub.

## After a sandbox reset
- **„fatal: not a git repository" nach einem Reset heißt NICHT, dass `.git` weg ist (2026-11-23).** Nach `git gc` stehen alle Refs in `.git/packed-refs`, und `.git/refs` enthält nur noch leere Ordner. Leere Ordner überleben einen Reset nicht – ohne `.git/refs` erkennt git den Ordner nicht mehr, obwohl Paket, `HEAD` und `packed-refs` vollständig da sind. **Reparatur: `npm run restore-git`** (oder von Hand `mkdir -p .git/refs/heads .git/refs/tags`), danach wie im übernächsten Punkt die Konfiguration. **Vorbeugung: die leere Datei `.git/refs/.keep`** – ein Ordner mit einer Datei übersteht den Reset, und git übergeht in `.git/refs` Namen, die mit einem Punkt beginnen (nachgestellt: nach gc + Reset findet git das Repo, Commit und gc lassen die Datei stehen). `npm run restore-git` legt sie bei jedem Lauf an; nach einem frischen Klon in der Sandbox einmal `npm run restore-git` oder `touch .git/refs/.keep`. **Nie `rm -rf .git`, nie das `.git` eines frischen Klons darüberkopieren**, solange `.git/objects/pack` ein Paket enthält: so wären am 2026-11-23 21 ungepushte Commits verloren gegangen – `tools/restore-git.sh` tat bis dahin genau das (`git rev-parse HEAD` schlug fehl → `rm -rf .git` → Klon von GitHub). Mit einem nur lokalen Commit in einem Probe-Ordner nachgestellt: altes Skript – Commit weg; neues Skript – Commit da.
- **Sandbox persistence:** if `.git` is really GONE (no folder at all – otherwise see the point above) or `src/assets/menu-bg.jpg` vanished after a reset, restore via `git clone --branch dev https://github.com/Cr0nFixXx/podracer.git /tmp/rc && cp -r /tmp/rc/.git . && mkdir -p src/assets && cp -n /tmp/rc/src/assets/menu-bg.jpg src/assets/` (working tree stays, shows as modified vs. `dev`; `dev` is the work branch since 2026-11-22, before that `B`). *(2026-11-22)*
- **Nach einem Sandbox-Reset** fehlt `.git/config`: `git config core.fileMode false` (sonst erscheinen alle Dateien als geändert – nur Dateirechte), `git remote add origin https://github.com/Cr0nFixXx/podracer.git` – beides und den Autor schreibt seit dem 2026-11-23 auch `npm run restore-git` (es erkennt den Reset am fehlenden Remote). Danach `git fetch origin --prune`. **Das Repo ist seit dem 2026-11-24 privat:** auch `git fetch` und die GitHub-API (Action-Läufe) brauchen jetzt den Zugangstoken des Nutzers – ohne ihn meldet `git fetch` „could not read Username" und die API 404. Der Token steht nur in dem einen Befehl (`git -c http.extraheader=… fetch`), nie in einer Datei, nie in der Remote-URL. Ohne Token weiterarbeiten geht: lokal committen, dem Nutzer sagen, was nur lokal liegt. Weg sind dann auch `node_modules`, `dist`, `build` und `tools/harness/out`: `npm ci`, vor einem Browser-Test `npm run harness:build`.
- Fehlt nach einem Reset doch einmal ein Commit: die Schritte aus dem Punkt darüber, `npm run check`, neu committen. Ein nur lokaler Commit ist erst sicher, wenn er gepusht ist – dem Nutzer sagen, wenn einer nur lokal liegt.
