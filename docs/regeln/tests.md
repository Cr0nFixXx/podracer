# Rules: checks, harness, browser tests

Part of the agent manual (`CLAUDE.md`). Read this before you run or change a check, use the harness, or test in a browser.

- The tag at the end of a rule is the session that wrote it; rules written after Session 20 carry their date. **If two rules disagree, the later one wins** (date > `S20 …` > `S19` > … > `≤ S9`).
- Rules without a tag come from the former "Testing" section of `CLAUDE.md`, which every session kept current.
- Sandbox limits for browser runs (2 GB RAM, software GL): `git-sandbox.md`.

## `npm run check`
- **GitHub runs the checks too:** `.github/workflows/check.yml` – `npm ci`, `npm run check`, `npm run build`, `npm run build:web` on every push to `dev` and every pull request into `main` (Node 20, as in the sandbox). `check:gpu` runs only when the workflow is started by hand with the box ticked; a failure there does not turn the run red. (On GitHub since 2026-11-22, `2d089ca`; the first run was green in 65 s: `npm ci` 3 s, `npm run check` 39 s, both builds 13 s, no warnings. The `gpu` job has never run. Actions used: `checkout@v7`, `setup-node@v7`.) The sim's teleport count leaves out exactly the one frame of a respawn (`prevInv` in `tools/ci/sim.ts`). *(2026-11-22)*
- **`npm run check`** (≈ 60 – 80 s in the 2-CPU sandbox, node only): typecheck (covers `src`, `tools/ci` and `tools/harness`), `tools/ci/unit.ts` (unit checks), `tools/ci/pods.ts` (pod audit, see `pods.md`), then `tools/ci/sim.ts` – fails on NaN, deaths > 3, wall penetration > 0.6 m, ground clearance < 0.2 m, pod slower than 18 m/s. `DEBUG=1`, `TRACK=<id>`, `SECS=<n>`, `PITCH_AIR=1|0|-1` (jump experiment).
- **Unit checks:** `tools/ci/unit.ts` (`npm run check:unit`, `ONLY=<text>`): tiny `test` / `eq` / `throws` helpers for pure logic. Write the check first, watch it fail, then the code. *(S20 Pods)* Renderer set-up can be checked the same way when it is geometry: `shadow:` builds the game's shadow rig in node (`csm._init({ camera, renderer: { coordinateSystem, reversedDepthBuffer } })` is all three's cascades need) and projects ground points through the shadow cameras. *(2026-11-23)*
- **The sim's tracks share one random stream:** a change that alters one track's run shifts every later row. Compare track by track (`TRACK=<id> node tools/ci/out/sim.mjs`) before calling a table change a regression. The deck self-test does not lift pod 1 in the last 2 s of a run (it would end before the 20 deck frames). *(S20 Strecken)*
- **One sim run cannot tell a small change from scatter – compare A against B over several seeds:** `SEED=<n> node tools/ci/out/sim.mjs` (default 1234567), with the switches `NO_BAYS=1` (one road width between rock borders), `NO_TUNNELS=1`, `NO_EXPAND=1`. On 2026-11-23 a first version of the bays looked like −3.6 m/s for the slowest pod at the default seed; over three seeds (1234567, 42, 777) it was −1.4 m/s (the final version: −0.5 m/s, average speed −0.2 m/s), while the seeds alone differ by 1 to 3 m/s. A row of means: `… | grep -E "^[a-z]+ +[0-9]+ +[0-9]+ +[0-9.]+m" | awk '{a+=$6; s+=$7; n++} END {print a/n, s/n}'`.
- **Session 20 (Pods) tests:** `npm run check:pods` (≈ 6 s; `POD=<id>`, `UPDATE=1`, `HULL=write` measures the hulls in `src/game/podHulls.json` again); harness `statsAll()` must match the audit numbers after any change to `podModel.ts` / `podAssembly.ts`; before/after sheets saved with `save:` are byte-identical when nothing visible changed.

## Which mesh is it? (a geometry defect in a screenshot)
- **`tools/harness/pdbg.mjs` does it (in the repo since 2026-11-23):** `cd /var/tmp/t && cp <repo>/tools/harness/pdbg.mjs . && timeout 900 node pdbg.mjs <repo>/tools/harness/out/game.html <track index> "<view>,<view>" /var/tmp/t/<prefix> "all,hide:terrain,only:ground+groundBlend"` → one picture per view and variant plus `<prefix>_grid.jpg`. Variants: `all`, `hide:<a>+<b>`, `only:<a>+<b>`, `wire` (terrain as wireframe), `trails` / `race` (powder snow). Names are material names – `road` (deck), `ground` / `groundBlend` (natural surfaces, solid / blended), `cliff` (wall sheets, rocks; on Aquilaris and Oovo IV the rocks are `rock`), `caveRock` / `tunnelWall` (inside of tunnels), `terrain`, `snow` – or the mesh name `borderRocks`. Per view it also prints `drawn: <meshes> meshes, <triangles> triangles`: every visible mesh in the view frustum, instances counted – the scene pass without the shadow passes. **Compare two builds with that line** (build the harness of the older commit into another folder: `git stash push -u`, `npm run harness:build`, `cp -r tools/harness/out /var/tmp/t/base_out`, `git stash pop`, build again); three's `info.render.triangles` mixes passes and frames and gave the same number for different views. On 2026-11-23 it showed in one run that an olive stripe of sand along the road was neither terrain nor the new shoulder but the drift band of `trackDetail.ts`. *(2026-11-23)*
- **"What is that thing in the picture?" → `pdbg.mjs` variant `pick:<x>_<y>+<x>_<y>`** (x, y from 0 to 1, origin top left; a run with only `pick:` makes no pictures). It names the first visible mesh under each point: object type, material name and type, geometry name, vertex attributes, vertex count, radius, distance, instance number, first vertex colour, instance colour (`window.pick` in `tools/harness/game.ts`). Give geometries a `name` – the view `g_<name>[_<instance>[_<distance × 10>]]` then flies to them (`fern`, `stone`, `pebbles`, `snowRock`, `scoria`, `ember` … have one). It also prints the hit point (`at=x_y_z`), the normal.y of the face and of its three vertices (a `terrain` face with `faceNy=0.00` a metre or two from the camera is the SKIRT of a terrain leaf: the camera is under ground – the view `g` stands 5 m outside the road edge at road height and is under ground on Frostspalt; the "smeared dark-blue streaks" there were never a defect of the game); the view `at_<x>_<y>_<z>_<tx>_<ty>_<tz>` puts the camera at one such point looking at another. A thin line needs a column of picks a few thousandths apart (`pick:0.60_0.250+0.60_0.256+…`): that is how the dark line across the Boonta tunnel turned out to be a gorge cable (`trackDetail.ts`, `cableMat`). On 2026-11-23 it showed within a minute that the "white untextured boulders" on Boonta were the ground-cover stones (vertex colour brown, yet light grey-blue in the shade under a blue sky) and that the "white eggs" beside a spire were the sand-coloured huts of `props.ts`, 115 m away – no defect. *(2026-11-23)*
- **"Something stands in the road" → `pdbg.mjs` variant `scan` (2026-11-23):** `node pdbg.mjs <game.html> <track> "p100_0_3_40_0_0_3" /var/tmp/t/sc "scan"` casts rays across every 4th sample of every path, parallel to the banked road at 1.5 m and 4 m, from 2.5 m inside one edge to the other, and lists the meshes they hit by stretch (≈ 2.5 min per track in the sandbox). `scan:0` lists the material names of the scene with mesh and triangle counts; `scan:<step>_<margin>_<a+b+c>` tests other materials (default: `cliff`, `cliffBlend`, `rock`, `terrain`, tunnel and cave rock – `cliff` includes the rock rows). Expected hits: the geyser towers of `hazards` (material `cliff`, they stand ON the road by design). The scan found the Methan-Derby bug in one run (terrain on samples 1208–1216, 1308–1316, 1704–1712, lat 0 … 29 of 35); the data-only probe (walls of the samples against other stretches) found nothing, because the geometry was terrain.

## Browser pane hidden (in-app browser)
- **Hidden browser pane, easier way (replaces stepping by hand):** right after `navigate`, before starting the race, give the page a timer-driven frame clock: `window.requestAnimationFrame = cb => setTimeout(() => cb(performance.now()), 16); window.cancelAnimationFrame = id => clearTimeout(id);` – game loop, three's frame counter and the WebGL2 fallback's shader-compile polling then run in real time (without it the WebGL2 app never leaves the loading screen while the pane is hidden). Then wait for `__podracer.state === 'race'`. *(S20 Pods)*
- **In-app browser pane hidden → `requestAnimationFrame` does not fire** (the race stays in the countdown). Step the game by hand: `const g = __podracer; g.keys.add('KeyW'); let now = g.lastT; for (…) { now += 1000 / 60; g.loop(now); cancelAnimationFrame(g.raf); }`, then `g.lastT = performance.now(); g.raf = requestAnimationFrame(g.loop);` – otherwise the next real frame gets a negative `dt` (`Game.loop` only caps it from above). Never cancel all rAF handles: three.js counts its frames in its own rAF loop, without it the camera uniforms freeze. Take pictures with the browser's screenshot tool (`canvas.toBlob` returns an old frame). Let the AI drive the own pod: `const m = await import('/src/game/physics.ts'); g.readInput = () => { const p = g.player; p.ai = { skill: 0.9, speedF: 0.9, lineOff: 0, takeShortcut: false, boostUntil: 0, repairMode: false, noiseT: 0, rubber: 1 }; m.aiInputs(p, g.td, g.pods, g.raceTime, null); p.ai = null; };`. The harness is unaffected (it renders with `renderAsync`). *(S20 Pods)*
